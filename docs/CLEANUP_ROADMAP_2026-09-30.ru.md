- Импорт ZIP пропускает JSON с ошибками. Затем handleDeletedPrompts удаляет отсутствующие публичные ID до syncPrompts; syncPrompts повторяет удаление. Общей транзакции удаления и вставки в просмотренных методах нет.

Удалённые branches/releases, доступность Issues, история VirusTotal и права на импортированный контент в рамках этого анализа не проверены. Сборка и тесты не запускались: работаем над планом. Существующие тесты FileRepositoryImpl и LLMInteractor сохраняются; наличие шаблонных Example-тестов не заменяет проверки данных.

## 4. Этап 1 — защитить данные и сделать релизы корректными

Приоритет P0. Оценка: 3–5 рабочих дней.

### 4.1. Room и импорт каталога

- Проверить реальные схемы поддерживаемых старых APK, восстановить корректный переход 4→5 и всю цепочку до текущей версии.
- Убрать destructive fallback для пользовательской БД после подготовки и тестирования миграций. Не исправлять пропущенную миграцию сбросом данных.
- Проверять архив целиком до изменения БД: формат, уникальные ID, обязательные поля, контрольная сумма при наличии manifest.
- При ошибке хотя бы одного обязательного файла отклонять обновление целиком. Пустой каталог принимать только как явно подтверждённый валидный snapshot.
- Удаление отсутствующих публичных записей и upsert выполнять одной Room-транзакцией. Убрать предварительное и повторное удаление.
- Не перехватывать CancellationException как обычную ошибку. Проверить закрытие response/streams и ограничения распаковки ZIP.
- Сохранять личные промпты и локальные метаданные; редактирование публичного промпта оформлять личной копией со ссылкой на источник.

Проверка: миграции поддерживаемых версий, повреждённый JSON, пустой/обрезанный архив, отмена, сбой между удалением и вставкой, обновление избранного. Во всех ошибочных случаях старая БД остаётся доступной и неизменной.

### 4.2. Android CI и release

- Разделить обычный CI и release. CI на PR/push: unit tests, lint, debug build.
- Release собирает commit выбранного тега, включая ручной запуск; не checkout master и не git pull после этого.
- Версию релиза брать из проверенного тега. Удалить автоматическое создание тегов из version.properties и обратный commit/push из release.
- Сохранить удобную локальную debug-версию. Проверить монотонность versionCode: текущая формула major*10000+minor*100+patch требует ограничений компонентов либо замены согласованной схемой.
- Release должен проходить проверки для того же SHA, что собирается. Проверять подпись, applicationId, versionName/versionCode; публиковать SHA исходников и SHA-256 APK.
- Не заменять существующий signing key ради очистки.

Примечание: push тега через GITHUB_TOKEN обычно не запускает новый push workflow. Поэтому текущая связка sync-version → release не должна считаться надёжной. Источник: https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow

### 4.3. Секреты и backup

- Определить назначение Vercel API: каталог, ratings, feedback. Для публичного чтения предпочесть публикуемые артефакты; для write endpoints определить настоящую авторизацию и защиту от злоупотреблений.
- Убрать общий секрет из APK после замены механизма доступа. Если действующий ключ уже распространялся, предусмотреть его ротацию.
- Проверить SecurePrefs и реальные имена файлов. Настроить backup и device transfer по фактическому размещению данных.
- БД содержит и промпты, и чаты: XML backup не исключает отдельные таблицы. Согласовать backup всей БД либо сделать управляемый экспорт разрешённых данных.
- Исключить токены и ключевой материал; проверить восстановление приложения без токенов, повторный вход и доступность личных промптов.
- Ограничить debug logging: не писать Authorization/X-API-Key, содержимое личных промптов, чатов и вложений.

Источник backup semantics: https://developer.android.com/identity/data/autobackup

Готово, когда: обновление не теряет данные, некорректный каталог не меняет БД, APK соответствует тегу, секреты не попадают в артефакт или backup.

Готово, когда: старый клиент читает ZIP, новый читает manifest/catalog, все исходные данные проходят проверку, повторная сборка даёт тот же каталог.

## 9. Этап 6 — optional sync после стабилизации

Приоритет P3. Оценка отдельно после проектирования; не входит в обязательную очистку.

- Сначала определить требования: какие данные синхронизируются, нужны ли чаты, как решать конфликты и удаления.
- Разделить публичный CatalogImporter и личный SyncEngine. Общий интерфейс провайдеров вводить под конкретный первый провайдер, не создавать пустые реализации для будущих сервисов.
- Room остаётся локальным источником данных. Изменение сущности и запись в журнал pending changes — одна транзакция.
- Для конфликтов хранить базовую синхронизированную версию/hash и remote concurrency token. revision и timestamp сами по себе не разрешают изменения двух устройств.
- Удаления передавать tombstones; определить срок хранения и поведение давно офлайн устройства.
- При конфликте сохранять обе версии; избегать молчаливого last-write-wins для текста.
- Выбрать GitHub auth после проверки актуальных capabilities, permissions и нужды в auth backend. Изложенную в старом аудите схему GitHub App не считать уже утверждённой реализацией.
- Для GitHub оценить один prompt на файл, batch commit, rate limits, повторное выполнение и конкурентную запись. Не создавать репозиторий или инфраструктуру автоматически в рамках cleanup.

Готово, когда: изменения двух устройств не теряются, удалённые данные не воскресают, повторы идемпотентны, отключение sync не блокирует локальную работу.

1. Inventory и сравнение Android-проектов, без удаления.
2. Защита импорта от частичного snapshot и атомарная транзакция.
3. Room migrations и тесты сохранения данных.
4. CI/release: точный tag SHA, отсутствие обратных push, версия и подпись.
5. Security/backup и изменение доступа Vercel API.
6. Один publisher каталога; старый ZIP остаётся доступен.
7. Schema/validator/builder и проверка существующего датасета.
8. Новый импорт manifest/catalog в Android.
9. Android dependencies/DI cleanup.
10. Архивирование legacy, README и contribution docs.
11. Личные копии и экспорт/импорт.
12. Optional sync как отдельный этап.

Для каждого изменения: конкретный diff, узкие проверки, способ отката. Согласовывать изменения контракта между репозиториями через совместимый переход, не одномоментный breaking release.

## 11. Проверки и сроки

Android после затронутых изменений: `gradlew.bat :app:compileDebugKotlin`, `:app:testDebugUnitTest`, `:app:lintDebug`, `:app:assembleDebug`. Room migration tests — на устройстве/эмуляторе через соответствующие instrumentation задачи. Release отдельно: сборка, проверка сертификата, установка поверх поддерживаемого APK и сравнение сохранённых данных.

Каталог: полный validator, повторная детерминированная сборка, проверка количества/ID/содержимого, импорт ZIP старым клиентом и JSON новым.

Оценка обязательных этапов 0–4: 11–20 рабочих дней одного разработчика. Это ориентир, а не обещание: время зависит от отличий проектов, миграций опубликованных версий и состояния датасета. Этап 5 ещё 3–5 дней. Sync, web-витрина и новые платформы оцениваются отдельно.

Ключевое условие завершения cleanup: один основной Android-клиент, компактный публичный каталог, восстановимые архивы, корректные релизы и отсутствие потери пользовательских данных при обновлении.
