# Android + Desktop: объединение приложений и управление каталогом

Дата: 30 сентября 2026. Заменяет прежнее предположение, что KMP desktop можно архивировать. Основной Android — `G:\Android\AndroidStudioProjects\aipromptmaster`, основной Desktop — `G:\Android\OpenideProjects\aiprompts\aiprompts-kmp`. Здесь предложена архитектура и порядок миграции; перенос исходников и изменения удалённых репозиториев пока не выполнены.

## Решение

Объединить приложения в один репозиторий AiPromptMaster; `aiprompts` оставить независимым публичным каталогом. Сначала собрать оба приложения в одном репозитории без переписывания, затем постепенно выделять общий KMP-код. Объединение репозитория, Gradle-сборки, моделей данных и UI — разные шаги с отдельными проверками.

Не архивировать поддерживаемый KMP Desktop. `AIPromptMasterCompose` остаётся кандидатом на архивирование после сверки уникальных изменений с основным Android.

## Что проверено в Desktop

- В settings.gradle.kts подключены `:shared` и `:desktopApp`.
- Оба модуля сейчас настроены только на `jvm("desktop")`; Android target отсутствует.
- Есть Room, Ktor, Koin, Decompose, Ollama, импорт/экспорт, классификация и scraper wizard, а также commonTest/desktopTest. Это существенная функциональность, которую нужно сохранить.
- В commonMain размещены java.io.File, java.util.UUID, ZIP APIs и другие JVM-зависимости; Selenium и jsoup объявлены в commonMain dependencies. Перед расширением targets необходимо разобрать платформенные границы. Android тоже JVM, но это не делает все desktop APIs и зависимости пригодными для Android или common metadata.
- Android использует Retrofit и Navigation 3, Desktop — Ktor и Decompose. Не нужно сразу менять оба стека или унифицировать всю навигацию.
- Модели Prompt похожи, но отличаются: Android использует java.util.Date и promptVariants, Desktop — kotlin.time.Instant и nullable content. Оба смешивают контент с isFavorite/isLocal.
- Desktop ExportPromptsUseCase включает isFavorite/isLocal и заметки в JSON. Такой пользовательский экспорт нельзя автоматически считать форматом публичного каталога.
- Desktop packaging настроен на Windows Exe. Сборка, запуск и упаковка сейчас не проверены; наличие конфигурации не подтверждает готовность артефакта.

## Целевая структура

```text
aipromptmaster/                 репозиторий приложений
  androidApp/                  действующий Android-клиент
  desktopApp/                  desktop entry point и упаковка
  shared/                      существующий Desktop shared на переходный период
  core/                        небольшой общий KMP-модуль
    commonMain/                контракт, модели, проверки, общие операции
    androidMain/               адаптеры Android по необходимости
    desktopMain/               адаптеры Desktop по необходимости
  catalogEditor/               desktop-инструменты подготовки каталога
  docs/
  .github/workflows/

aiprompts/                     независимый репозиторий данных
  prompts/
  schema/
  scripts/
  docs/
  .github/workflows/
```

Это целевое направление, не команда сразу создать все модули. На первом шаге допустимы два Gradle root в одном репозитории; один root вводится после согласования toolchain. Название `core` уточнить при реализации. `catalogEditor` выделять, когда граница desktop curator tools действительно потребует собственного модуля.

Общий код: DTO каталога, стабильные ID, преобразования, валидация, работа с variables/variants, проверки snapshot, правила личных копий и локальных метаданных. Позже — сетевое чтение каталога и часть repository/data логики.

Платформенный код: file picker, Android SAF/URI permissions, desktop paths, secure storage, database builder, background work, notifications, installer, signing. Selenium/browser scraping — Desktop. Пользовательский UI может оставаться разным: Android для touch, Desktop для клавиатуры, мыши и массовых операций.

KMP допускает постепенное выделение общей логики и платформенных реализаций: https://kotlinlang.org/docs/multiplatform/multiplatform-share-on-platforms.html

Room может использоваться в KMP, но перенос текущих баз должен сохранять их реальные схемы и миграции; не заменять Android DB desktop-схемой. Источник: https://developer.android.com/kotlin/multiplatform/room

## Как управлять промптами

### Три независимых вида данных

1. **Публичный каталог:** исходные JSON в `aiprompts/prompts/`, стабильные ID, языковые версии, variants, variables, происхождение, лицензия и версия формата.
2. **Личные данные:** локальная БД приложения, собственные ID, личные копии с sourcePromptId. Отдельный versioned export/backup, optional sync позже.
3. **Локальное состояние:** избранное, пользовательские теги, история использования и заметки. Обновление каталога его не перезаписывает.

Room приложения — локальное рабочее хранилище. Git JSON — источник опубликованного каталога. Сгенерированные catalog.json/ZIP — артефакты распространения. Сырые scraper results — черновики, не опубликованные данные.

### Desktop как редактор каталога

Сохранить и развить существующие импорт, классификацию и scraper wizard вместо создания ещё одного редактора с нуля.

Путь куратора:

```text
источник/ручной ввод → черновик → редактирование → проверка
→ diff выбранных изменений → запись в локальный checkout aiprompts
→ PR/ревью → CI → merge → публикация catalog/manifest/ZIP
```

- Пользователь явно выбирает локальный checkout каталога. Репозиторий не определяется жёстким путём на компьютере разработчика.
- Развести режимы «мои промпты» и «редактирование каталога». Публикация личного промпта требует явного выбора записи и проверки удаляемых приватных полей.
- MVP работает с локальными файлами и показывает diff; Git push/PR automation добавляется отдельно. Не нужны backend и GitHub auth в первом шаге.
- Экспортёр публичных DTO использует whitelist полей. isFavorite, isLocal, заметки, токены и sync metadata не попадают в каталог.
- Перед записью: validate всех выбранных записей, проверка коллизий ID/путей, обнаружение внешних изменений с момента чтения. Запись файла через временный файл и atomic replace, где поддерживается; ошибки batch не должны маскироваться как полный успех.
- При обновлении промпта ID сохраняется. Переименование/перенос категории не создаёт новый ID. Похожие тексты показываются для ручной оценки, а не удаляются автоматически.
- Источник и права проверяются до публикации. Автоматическая классификация — подсказка редактору.

### Публикация и загрузка

- Один validator и builder, используемые локально и в CI.
- JSON Schema описывает реальный RU/EN content, variants и variables обоих приложений.
- Для PR: schema validation, уникальность ID, отчёт добавлений/изменений/удалений. Подготовленные автором generated files не заменяют сборку CI.
- Детерминированный catalog.json, manifest с version/hash/source commit, checksum и совместимый prompts.zip.
- Версионированные snapshots неизменяемые; стабильный указатель обновляется после успешной сборки всех артефактов. Клиент проверяет hash и повторяет загрузку при несовпадении.
- Сохранить releases/download/latest-prompts/prompts.zip для старых клиентов. Не менять данные и потребителей одновременно несовместимым образом.
- Клиенты проверяют полный snapshot до изменения БД и импортируют одной транзакцией. Частичный parse не является основанием для удаления отсутствующих ID.

## Порядок выполнения и критерии готовности

### 1. Baseline и сохранение

Сохранить историю и dirty/ignored файлы, включая пользовательское изменение KMP gradle.properties. Проверить команды compile/test/run/package Desktop и Android compile/test/lint/assemble. Зафиксировать отдельно результаты и исходные ошибки. Не обещать успешный baseline по наличию кода.

Готово: обе исходные версии восстанавливаются, известны поддерживаемые сборки и сценарии, составлен список уникальных функций.

### 2. Один репозиторий приложений

Предпочтительно сохранить существующий origin aipromptmaster и Android history. Перенести Desktop subtree с историей; выбрать способ переноса после проверки Git-history. Старое расположение пометить как перенесённое только после успешной проверки. Prompt dataset history остаётся в aiprompts.

Сначала допускаются независимые Gradle roots и CI jobs. Затем зафиксировать совместимые Kotlin/Compose/AGP/KSP/Room/JDK/Gradle версии и перейти к одному root. Не повышать Android minSdk и не менять подпись ради переноса.

Готово: Android и Desktop собираются из одного репозитория, имеют независимые проверки и релизы; поддерживаемый код не дублируется между репозиториями.

### 3. Общий контракт

Выделить первый небольшой KMP core с Android/Desktop targets. Сначала общий CatalogPrompt DTO и проверки; адаптеры переводят его в существующие модели приложений. Сохранить варианты и многоязычность. Написать совместимые fixtures по фактическим JSON.

Готово: оба клиента читают одинаковые fixtures, ID и содержимое сохраняются, старый ZIP поддерживается.

### 4. Безопасный общий импорт

Исправить риски транзакций и Room миграций до объединения хранилищ. Вынести общую проверку manifest/hash/snapshot. На первом шаге оставить разные repository/storage реализации; затем решать, какую часть Room действительно выгодно объединить.

Готово: повреждённый архив, несовместимый формат, отмена и сетевой сбой не меняют прежнюю БД. Личные копии и избранное сохраняются на обеих платформах.

### 5. Редактор каталога

Развести private export и public export. Подключить локальный checkout, черновики, валидацию, diff и безопасную запись. Затем упростить aiprompts до данных, schema, scripts и документации; legacy Python отдельно архивировать после проверки.

Готово: Desktop создаёт и меняет публичный промпт, CI принимает результат, оба клиента получают обновление без потери локальных данных.

### 6. Постепенное сокращение дублей

Общие операции поиска/variables/редактирования и UI-компоненты переносить по одному, когда поведение совпадает. Retrofit/Ktor, Navigation 3/Decompose и OpenRouter/Ollama сначала скрыть за подходящими интерфейсами. Не заставлять Android использовать scraper или Desktop — Android permissions.

Готово: общая логика проверяется один раз в core, platform adapters — своими тестами; пользователи не теряют существующие функции.

## Что не нужно делать в первом цикле

- Переписывать сразу весь UI на единый Compose экран.
- Заменять одну БД другой или сбрасывать данные.
- Обновлять все зависимости до новейших одновременно с переносом.
- Добавлять iOS, backend, GitHub private sync, web-витрину и десятки модулей.
- Удалять KMP Desktop, его тесты и инструменты подготовки каталога.

Первый проверяемый результат: оба приложения в одном репозитории плюс небольшой общий модуль контракта, отдельный каталог и работающий путь подготовки/публикации промптов. Срок полной унификации оценивать после baseline и проверки Android target; прежняя оценка cleanup для этого не подходит.
